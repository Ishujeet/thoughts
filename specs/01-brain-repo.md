# 01 — Brain repository

Status: Draft

## Purpose

Define the on-disk layout of a brain, where it lives on a developer's machine, and how a code repo attaches to it. Everything else in the CLI depends on this layout.

## Locations

| Thing | Path | Notes |
|-------|------|-------|
| Global config | `~/.config/thoughts/config.yml` | Known brains, default user id, integration credential refs, per-brain user options (`store_commits`), and `attached[]`: every initialised repo path on this machine with its `repo_id`, brain, and `initialised_at`. |
| Brain clones | `~/.thoughts/brains/<brain-id>/` | One per brain: a clone (git backend) or a backend workspace (psql, nebula — see [Backends](#backends)). `brain-id` defaults to the repo name of the brain remote. |
| Repo config | `<repo>/.thoughts.yml` | Committed. Says which brain this repo belongs to and its repo-id. |
| Symlink | `<repo>/thoughts` → `~/.thoughts/brains/<brain-id>/` | Gitignored. Created by `init`. |

The symlink target MUST be the brain root, not a subdirectory, so that `thoughts/shared/...` and `thoughts/repos/<other-repo>/...` are reachable from any attached repo.

## Backends

A brain is held in one **backend** — its durable store and sync transport (D22). The backend is chosen at `init` and is immutable in v1. In every backend, thoughts remain OKF markdown documents with YAML frontmatter.

| Kind | Store | Sync transport |
|------|-------|----------------|
| `git` (default) | a plain git repository (remote) | `git pull --rebase` / `git push` |
| `psql` | a PostgreSQL database | single transaction, optimistic `base_rev` check |
| `nebula` | a NebulaGraph space (nGQL) | statements applied store-wins |

The workspace at `~/.thoughts/brains/<brain-id>/` is the **working set for every backend**: a clone of the git remote for `git`, and a CLI-materialised copy of the same layout for the non-git backends. Layout, zones, and OKF rules below are identical in all three. Provisioning, connection references, and per-backend sync semantics are defined in [16-brain-backends.md](16-brain-backends.md).

## Brain layout

```
<brain>/
  index.md                  # generated: root index, declares okf_version
  log.md                    # generated: chronological changelog
  brain.yml                 # brain-level config (name, repos, integrations, template source)
  templates/                # optional org overrides; absent → CLI built-ins used
    plan.md
    spec.md
    research.md
    decision.md
    pr.md
    commit.md
  standard/                 # optional org override of the standard kit (see 08)
    skills/
    agents/
    commands/
    instructions/
  shared/                   # project-wide thoughts, not owned by one repo
    index.md                # generated
    plans/
    specs/
    research/
    decisions/
  repos/
    <repo-id>/              # owned by one code repo
      index.md              # generated
      plans/
      specs/
      research/
      decisions/
      prs/
      codegraph/            # generated: this repo's code graph (spec [17](17-codegraph.md)), never hand-edited
  users/                    # optional personal scratch, one dir per user id
    <user-id>/
      index.md
      ...
```

Rules:

- `shared/`, `repos/`, `users/` are the three **zones**. Every thought lives in exactly one zone.
- Every thought is an OKF concept: a `.md` file with YAML frontmatter as defined in [09-index-metadata-okf.md](09-index-metadata-okf.md).
- Subdirectories under a zone (`plans/`, `specs/`, …) are **kinds**. The default kinds are `plans`, `specs`, `research`, `decisions`, `prs`. `brain.yml` MAY declare additional kinds; each kind maps to a template.
- `index.md` files are generated by the CLI and SHOULD NOT be hand-edited. `thoughts sync` regenerates them before committing.
- `repos/<id>/codegraph/` is generated data: the code graph of that code repo (see [17-codegraph.md](17-codegraph.md)). It is never hand-edited and is rebuilt by `sync`.
- A brain MAY be empty of `templates/` and `standard/`. The CLI then uses its built-in defaults.

## `brain.yml`

```yaml
okf_version: "0.2"
kind: project              # project (v1) | org (reserved, see "Future: org-level brains")
name: acme-checkout
description: Checkout platform — orders, payments, notifications
backend:                     # durable store of this brain (see Backends); git is the default
  kind: git                  # git | psql | nebula; immutable after init in v1
  # database: acme_brain     # psql only: database name (non-secret descriptor)
  # space: acme_brain        # nebula only: space name (non-secret descriptor)
repos:
  - id: orders-service
    remote: git@github.com:acme/orders-service.git
  - id: payments-api
    remote: git@github.com:acme/payments-api.git
kinds:                       # optional; defaults shown
  plans: { template: plan }
  specs: { template: spec }
  research: { template: research }
  decisions: { template: decision }
  prs: { template: pr }
integrations:                # see 10-integrations.md
  github:
    org: acme
  jira:
    site: acme.atlassian.net
    project_keys: [CHK]
templates:
  source: builtin            # builtin | brain | path:<dir> | git:<url>
```

- `kind` defaults to `project` when absent, so brains created before the field existed keep working.
- `backend.kind` defaults to `git` when absent, so brains created before the field existed keep working. It carries a non-secret descriptor only (`database` for psql, `space` for nebula); connection strings NEVER go into `brain.yml` — they are referenced from global config as a cred-ref (see [16-brain-backends.md](16-brain-backends.md), [15-secret-scanning.md](15-secret-scanning.md)).
- `repos[].id` MUST be unique and MUST match `<repo>/.thoughts.yml` `repo_id`. Default is the code repo's directory/remote name.
- `init` appends to `repos` when a new repo attaches. This is the only automated edit to `brain.yml`.

## `<repo>/.thoughts.yml`

```yaml
brain: git@github.com:acme/acme-brain.git   # remote URL; id derived from it
repo_id: payments-api
tools: [claude-code, codex]                  # union of tools any teammate set up; init appends
kit_version: 0.3.0                           # CLI version that last installed/updated the kit
```

Committed to the code repo so teammates get the same brain and repo id on `thoughts init` without being asked; they still choose their own tools and integrations in the sub-guides.

## Ownership and write rules

- A repo's assistant SHOULD write only under `repos/<its-id>/`, `shared/`, and `users/<me>/`.
- Writing under another repo's directory is allowed (git does not stop it) but the standard kit instructs assistants not to, and `thoughts status` flags cross-repo edits in the working tree as a warning.
- `shared/decisions/` is the canonical home for cross-repo decisions. A decision that affects two repos goes to `shared/`, not to both repos.

## Symlink behaviour

- `init` creates `<repo>/thoughts` as a symlink and adds `/thoughts` to `<repo>/.gitignore` if not present.
- Supported platforms are macOS and Linux (D4). On any other platform `init` MUST exit with a message stating that, before touching disk.
- If `<repo>/thoughts` already exists and is not a symlink to the expected brain, `init` MUST refuse unless `--force`.

## `users/` zone

Personal scratch lives in the brain, under `users/<user-id>/`, and syncs like everything else (D7). The brain is one entity for everyone; there is no per-user exclusion. Personal drafts are still visible project-wide, which is the intent: half-formed thinking is context too. The standard kit tells assistants to treat `users/` content as lower-trust than `repos/` and `shared/`.

## Future: org-level brains

Not built in v1, but v1 MUST NOT paint us into a corner (D3). Reserved design:

```
<org-brain>/
  brain.yml                 # kind: org
  index.md
  shared/                   # org-wide decisions, standards
  projects/
    <project-name>/         # a complete project-brain layout, unchanged from v1
      brain.yml             # kind: project
      shared/  repos/  users/  templates/  standard/
```

Backward-compatibility rules that v1 code MUST follow so this can land later:

- All bundle-relative paths in frontmatter and indexes are relative to the **project brain root**, never to a filesystem path. An org brain re-roots them under `projects/<name>/`.
- Config resolution is a lookup chain (`repo → project brain → org brain → global`), implemented as a chain from day one even though v1 has two links.
- `<repo>/.thoughts.yml` gets an optional `project:` field, ignored in v1.
- Template and standard-kit resolution checks the project brain first, then the org brain, then built-ins. v1 implements "project, then built-ins"; the middle link is a no-op slot.

## Multiple brains

A developer MAY have several brains cloned (one per project). Each repo points at exactly one. `thoughts` commands run from inside a repo resolve the brain via `.thoughts.yml`; run from elsewhere they take `--brain <id>` or the `default_brain` in global config.
